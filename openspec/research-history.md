| research-003 | `research-003-track-parse-freshness-and-capabilities` | outdoor/tracks-metadata | Investigated how a stored GPX parse declares what it was produced with and how the owner learns that a parse is out of date. Recommended an **additive parser capability list** in `gpxParse` (what the parser can produce, not what one file contained) rather than an envelope-version bump, because `TRACK_GPX_METADATA_VERSION` gates the whole summary and a bump would hide every existing parse; a parser revision was rejected as the source of truth but kept as an optional diagnostic. Defined staleness rules that distinguish an old parser from a file without `<time>`, a single owner-only **Update track data** action that replaces per-feature refresh buttons, and reparse safety: only `GPX` file-based tracks, preserve `timeSource` and a confirmed timezone, never reparse `MANUAL`/`NONE` rows. Recommended computing stops and per-kilometre splits at parse time because the stored `timeline` is capped at 400 points, and treated a public parsing-features page as optional docs communication rather than the freshness mechanism. Delivered the follow-up candidates `parse-capabilities-and-update-action` (P0), the device, stops, and pace capability notes, and `public-track-data-guide` (P1). Pure research, no code changes. Output: [`openspec/changes/archive/2026-11-22-research-003-track-parse-freshness-and-capabilities/output.md`](./changes/archive/2026-11-22-research-003-track-parse-freshness-and-capabilities/output.md). |
